# `fig` version 6.0.0

A new major version for Fig, but still under the "Texas Everbearing" epoch. Rather than go a new direction, it takes the ideas behind the previous epoch even farther.

In the [previous devlog](../2-texas-everbearing/2-texas-everbearing.md), I added the ability for Fig to understand different languages at runtime. In Fig 6, the core now knows nothing about any specific format. Consumers must use separate language modules like `fig-json`.

Typically, this would slow down performance, but thanks to the new design, this actually increased performance in nearly all cases.


## Faster on every command

In 5.2, a language's parse handed back its own table of 144-byte rows, and Fig copied it into a tree.
In 6.0 the table *is* the document: 32-byte rows that the language fills through Fig's calls, adopted as they stand with no copy.

For runtime languages, the only copy is across the RPC layer. For compiled languages, copies and allocations are near the floor. JSON in particular has now become a pull parser, making Fig parsing time competitive with `jq` and `jaq`.

![Wall time of fig 5.2 and 6.0 on a large YAML and JSON file](6-0-0-speed.svg)

These are files of 30,000 services each (YAML 4.5 MB, JSON 7.3 MB), timed from process start.
On a small file, both versions take about 3 ms, most of it starting the process.

5.2 had a TOML bug where appending to an array of tables walked the whole array first, so every `[[services]]` cost more than the one before it.
On a 4.5 MB file that is seconds per command.
6.0 appends in constant time, and replacing one value is 34× faster.

![Wall time of fig 5.2 and 6.0 on a large TOML file](6-0-0-toml.svg)

YAML takes about a quarter of the memory it took before, and JSON about a ninth.

![Peak memory of fig 5.2 and 6.0 on a large YAML, JSON and TOML file](6-0-0-memory.svg)

## A core that names no language

Every format now registers with the core the same way a language written in JavaScript or Lua does, and gets back a handle.
`Format.Yaml` is gone; `formatByName("yaml")` finds whatever registered under that name.

![In 5.2 ten formats were compiled into the core; in 6.0 each one registers](6-0-0-core.svg)

The payoff is that a language is now a package of its own.
YAML is one Zig parser and printer, and it ships as the `fig-yaml` crate, the `@diaryx/fig-yaml` npm package (Fig's own Zig, compiled to its own WebAssembly module), a `libfig_yaml.a` for C, or built into the CLI.
You take the languages you use and nothing else.
`fig-sys` and `libfig` carry no language by themselves.

A few other things moved to make that work:

- **The authoring dialect is `figl`.** `fig` is the library's name and no format's. `-i fig` finds nothing now; write `-i figl`.
- **plist is built in by default.** It used to need `-Dplist=true`. If you had configured a helper named `plist` in `languages.figl`, Fig now refuses it as a taken name; build with `-Dplist=false` to give the name back.
- **Helpers speak [JSON-RPC 2.0](../../helper-protocol.md).** A helper built with `fig::helper::serve` or `@diaryx/fig/helper` needs a rebuild and nothing else.
- **Embedding has left Fig.** Fig reads and edits a config document, not the Markdown or HTML file it sits in. [twig](https://github.com/diaryx-org/twig) finds frontmatter and fenced blocks now, and you hand their contents to Fig's `Editor`.

This is a breaking release for every binding, which is why it is 6.0.
[Migrating to 6.0](../../migrating-to-6.md) has a table for each one, and [the proposal](../../proposals/core-only.md) has the argument.

## Change one value, and only that value

The purpose of Fig is to have the smallest possible programmatically driven diffs.

Here is a diff comparison with Fig and other tools:

![Lines changed when each tool sets one value](6-0-0-fidelity.svg)

Fig has the smallest possible diff at 2 lines.
yq loses a blank line and a comment in YAML, and in JSON turns the 20-digit integer into `1.2345…e+19`.
dasel drops comments and turns `0x1F` into `31`, and refuses the JSON file outright.
jq and jaq keep every number as written, but reflow the whole file, and gojq sorts every object's keys too.

## Next to jq, jaq, gojq, yq and dasel

jq is a full query and transform language: JSON in, JSON out.
It never edits a file in place, and it isn't trying to.
yq and dasel bring that model to more formats.
Fig is a set of editing verbs over paths (`get`, `set`, `replace`, `rename`, `delete`, `patch`), made for files people wrote by hand.
It is also a library for Rust, TypeScript, C and Zig, and figl has a language server. Its set of formats is open-ended.

Against yq 4.53 and dasel 3.11, Fig is 2–5× faster on every command and format, and usually uses less memory.
yq's TOML reader has the same flaw 5.2 had: 1,000 `[[services]]` take it 5.5 s, and 4,000 take 106 s.

On raw JSON, the jq family is much closer, and jaq is the one to beat.
Here is the 7.3 MB file again. Get reads the last service's name, and replace sets one service's `weight`. Fig writes the file; jq, jaq and gojq print the whole document to stdout, since none of them edit in place.

| | get | replace |
|---|---|---|
| fig 6.0 | 0.039 s · 37 MB | 0.081 s · 87 MB |
| jaq 3.1 | **0.033 s** · 62 MB | 0.087 s · **62 MB** |
| gojq 0.12 | 0.060 s · 46 MB | 0.101 s · 60 MB |
| jq 1.7.1 | 0.141 s · 55 MB | 0.312 s · 58 MB |

jaq reads JSON faster than Fig does.
And on a replace, all three use less memory than Fig, because Fig keeps the source and every span it needs to write your edit back in place.

TLDR; If you are wrangling JSON in a pipeline and don't care how the output is spelled, jaq is excellent and you should use it.

Next, I want `replace` to keep a string's quote style the way `patch` now keeps a number's spelling.
That one is still [a proposal](../../proposals/keep-quote-style.md).

Please enjoy the new Fig update!
